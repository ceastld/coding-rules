# 产品持续迭代

将开发闭环围绕用户能观察到的结果组织起来。技术栈、构建命令、交付方式和权限从当前项目取得；本 skill 不绑定某个仓库、平台、分支或外部审查服务。

## 确定本次范围

用户指定的任务优先。区分一次性任务与明确授权的长期迭代：一次性任务完成后交付；长期迭代完成一个阶段后更新记录并继续计划中下一项。宿主支持持久目标时，读取已有目标并保留整体完成条件，阶段成果不能结束长期目标；没有这项能力时沿用项目计划，普通迭代请求不自行创建持久目标。

仅评估流程价值时使用价值评估参考，停留在分析范围，不启动实现或交付闭环。

先读取适用的项目指令文件（如 AGENTS.md）、当前交接摘要和任务有关的计划，再看当前实现。项目使用 Git 时检查 git status；其它项目检查现有变更，保留已有改动。历史日志按疑点检索；遵守项目必读入口，但读取被截断时继续定位所需段落，不把截断结果当完整证据。

从现有资料确定：

- 当前用户问题、目标人群与成功条件。
- 本次允许改变的范围、架构与数据合同。
- 既有实现、验证入口、当前有效回执和未验范围。
- 交付授权、实际验证限制及并行修改的归属。

资料已有答案时直接执行。缺少影响结果的需求时先询问，并继续不依赖答案的工作。项目没有专用计划或脚本时沿用现有文档与工具，只有重复使用的实际需求才增设设施。

## 选择有价值的切片

裸“继续迭代”从当前计划选下一项；明确任务不被 backlog 替换。比较用户影响、已有反馈、实现成本和依赖，优先解决已证实的阻碍、数据错误或高频操作问题。缺乏使用数据时明确这是基于需求的判断。

切片应具有完整的用户结果：用一句话写清“在什么入口与状态下，用户做什么，期望发生什么”。范围够小以便交付，但包含必要的数据流、交互与输出；只加按钮或只做模型，若用户路径未接通，记录为阶段而非功能完成。

参考产品用于发现合同与遗漏，实际设计服从当前用户需求和架构。不要把参考产品的界面或模块顺序当通用要求。

## 实现与协作

复用现有边界和适配层。独立子任务可并行，给出目标、输入、接口和文件归属；共同修改热点文件时采用项目已有的隔离方式，由一个集成者整合。工作树和隔离目录服务于实际冲突，不作为每个小改动的固定步骤。

确定性的重复步骤优先调用已有脚本；Agent 负责取舍、归因与审查。新增脚本应减少真实重复劳动，简单工作沿用现有计划和工具；只有实际需求证明值得时才建设任务管理设施。

按项目既有形式同步实际改变的功能说明、入口或快捷键。核验成果先读取文件与回执；需要新的具体任务或澄清新证据时，在已有授权内联系协作方。

## 验证与审查

按变更影响选择能证明结果的检查，遵守项目必须执行的门禁。验证范围包含实际工作树中的本次修改；已有他人修改时使用项目支持的路径或快照边界，不能只检查已提交内容来替代未提交实现。

通过的检查在相关代码、依赖、配置和基础未变时复用；进入新阶段、提交相同内容或改文档不自动重编。修复或相关输入变化只重跑失效的检查。并行修改期间需整仓构建或交付时，绑定稳定源码与产物；无关变化不抹掉局部有效结果，也不能使它变成当前整仓通过。

读取实际终态、断言和输出。进程成功、零匹配测试、模型自报或工具调用出现，不自动证明目标通过；工具外层成功时仍检查业务结果。区分模型检查、真实运行、GUI、安装与发布的资格，分别记录对应版本或来源。

自审聚焦合同、状态、错误恢复、资源生命周期、数据与用户路径。指出问题须有当前义务、变更因果、可达失败和比例适当的修正。无具体缺陷可以直接说明；不为凑审查数量添加假设性问题。

修复本次引入的有效缺陷，复验受影响路径。无关旧失败单独记录；不为转绿削弱有效断言或隐藏失败。

## 交付与继续

交付由当前会话授权和项目规则决定。自动迭代不会凭 skill 自行授予 commit、push、PR、合并、安装、发布或向他人发消息的权限；已取得的授权保持有效，也不每阶段重新询问。

明确交付目标所必需的常规步骤按会话与项目规则处理，更具体的限制优先；创建 PR 的授权不自动包含合并。区分可以提交审阅的结果与已经满足发布或合并门禁的结果。

默认先完成已授权的本地实现、检查与可审阅结果。已授权的 PR 或交付闭环持续推进至约定终点；未授权的外部步骤不挡住本地开发。发布或合并的前置检查按项目合同执行，不硬编码云审服务、重试次数或分支。

结果用现有交接位置简短记录：用户行为变化、实现与集成状态、实际验证及来源、未验项、下一项。详细日志保留于证据目录，交接摘要只放当前状态和链接。

真实验证暂不可用时，先判断它阻止哪种完成或发布结论：只影响 GUI 资格则保留待验并继续独立功能；影响数据合同或安全交付则先解决该部分。遵守用户对前台、真实数据及环境的限制，不重复要求已拒绝的操作。

长期迭代在当前执行中继续可推进任务；没有可切任务、重复阻碍无新证据或需要用户决策时说明具体原因。跨时段继续需要用户请求的自动化或新的调用，skill 文本不等于后台调度。用户暂停或取消时停止。

## 根据结果改进方法

用户反馈先查真实版本、入口、状态和期望，再归因到能力缺口、交互/引导、实现缺陷或环境限制；AI 产品还需区分知识、路由、推理与工具运行时。修改导致问题的层，不用更长提示词掩盖产品缺陷。

需要评估迭代价值、归因反馈或优化产品内 AI 行为时，读 [价值与学习](references/value-and-learning.md)。将已证实、可重复的经验沉淀为简短合同或示例；局部事故和个人项目惯例保留在项目层。
