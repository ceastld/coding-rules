# 判断产品迭代与流程的价值

在需要评估自动迭代是否值得、整理用户反馈或优化 AI 产品时读取。普通功能修改不要求创建度量系统或运行此处全部实验。

## 产品收益与流程成本

为当前切片选一个直接反映用户任务的观察量，再选择一个能暴露主要代价的观察量。使用现有回执；样本不足就写待观察，不编造收益。

| 问题 | 合适的观察量 | 不能直接替代它的量 |
| --- | --- | --- |
| 用户能否完成任务 | 代表性输入上的实际成功与失败、恢复结果 | 提交数、按钮数、测试定义数 |
| 是否更省时间 | 同口径的端到端耗时、交互步骤 | 单一算法耗时或下载耗时 |
| 功能是否稳定 | 同类真实问题是否复发、支持路径是否回归 | 仅编译成功或模型自报 |
| 流程是否减少人力 | 必须由人处理的澄清、修复和协调次数 | 子 Agent 数或自动调用数 |
| 流程开销是否合算 | 功能周期、构建/审查等待、重复验证与可得的实际用量 | 文档字符数推算的账单收益 |

工程指标是线索：fix/feat 比、PR 周期和短期回修可帮助定位问题，但相同 scope 的临近修复不证明因果，快速合入不证明用户体验改善。区分历史基线、当前观察与预测。

对功能的验证以当前需求合同为准；对流程的收益判断宜比较相近规模、同技术栈与同验证等级的任务，并说明样本和限制。不能把轻任务与难任务的差异归为 skill 收益。

当流程耗时持续增长而用户结果无改善，先检查必读上下文、重复构建、并行冲突与无证据审查。删减重复步骤、将确定性操作交给已有脚本、压缩当前状态入口，详细历史保留可检索链接。不要因为流程繁重就取消必要验收。

## 从真实反馈形成任务

先确认反馈的产品版本、运行入口、实际能力、用户目标和执行记录。同一句需求在不同入口可能有不同合同。缺附件、记录过期或无法复现时降低结论置信度。

逐项对照实现和业务结果：外层工具成功可能只意味着调用没有抛异常；内层失败、空结果和未落盘应按实际语义解释。按根因聚合已有任务，避免同一问题重复建项。

建议的任务表述：

> 在已支持的入口和输入下，现行为造成某个用户影响；证据在某处。最小修正改变某条路径，验收用可观察结果判断；尚不确定的条件单独列出。

任务由用户结果决定，修复层由证据决定。有意的产品限制由产品范围决定是否调整；引导不足可以单独修复。确认无缺陷或重复反馈也可以结束归因。

## 仅适用于 AI 产品的优化

区分受测产品 Agent 与执行开发的 Agent。在隔离评测环境运行有真实检查器的代表性任务；正常用户环境中的写操作仍服从原授权。

- 能力已存在但知识不可发现：修描述、检索入口或技能示例。
- 资料正确但选错工具：修路由或明确的使用合同。
- 工具返回误导、运行时错误或持久化失败：修实际工具实现。
- 产品本身缺能力：按产品需求实现，不能只补提示词。

修改前保留基线；修改后核实实际运行实例已经加载新来源，再比较同组结果与相关回归。单个失败用例转绿只是局部证据。用于训练/调试的例子与保留评测任务分开，避免把完整标准答案塞进 skill。

相同失败反复靠提示词修补且没有整体收益时，重新检查归因、工具合同或能力边界；不累积无限禁令。沉淀正向可复用的模式和不同意图的示例，维持上下文精简。
